# Application identity and signing audit

Baseline: `f8df11ac3b019d022d3fa4a1b39c1b2f8576d361`, inspected 2026-10-02.
No identifiers, credentials, native source, or signing code changed in bootstrap.
Paths in this document are relative to `SparkyFitnessMobile/` unless prefixed with
another repository directory. Generated projects were inspected in a disposable
worktree after production Android/iOS and development iOS prebuilds.

Classification:

1. Already configurable or derived from runtime/configuration.
2. Hardcoded identity/integration value that should become configurable.
3. Upstream/internal identifier or attribution that should remain untouched.
4. Persistent or security-sensitive contract that is dangerous to change casually.

An item in class 1 or 2 can also have an upgrade/signing consequence; the consequence
is recorded explicitly. New fork identities will not update installations signed
as upstream applications. Register our identities before distributing binaries.

## EAS and CI dependencies

`eas.json` defines development (development client/internal distribution), preview
(internal distribution using production identity), and production (Android AAB,
iOS medium runner, automatic remote build-number increment). There is no explicit
`credentialsSource`, EAS Update URL/channel configuration, or separate fork owner.
Provision and verify credentials for the host plus every Apple target. Expo's
[app-extension documentation](https://docs.expo.dev/build-reference/app-extensions/)
describes the extension metadata EAS needs before credential generation; inspect
what the installed target plugins actually emit before adding parallel declarations.

## Future Wear identity

For a phone-relayed Wear OS application, Google Data Layer requires the phone and
Watch to share application ID and signing certificate. Reserve that relationship
now; the Wear Kotlin namespace can still differ. Plan Play App Signing versus
sideload certificate continuity before distributing either binary. This is a
verified platform constraint, not a proposed upstream implementation:
[Data Layer security](https://developer.android.com/training/wearables/data/overview#security_of_communications).
